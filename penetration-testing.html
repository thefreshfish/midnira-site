Rules of engagement

The terms every test runs under

  1. Written authorization comes first. No testing starts without a signed scope, a test window and emergency contacts.

  2. Agents stay in scope. Targets are checked against the authorization before an agent touches them, and every action is logged.

  3. A person validates every finding. Nothing goes into your report on an agent's word alone.

  4. Nothing disruptive without consent. Techniques that could affect availability or data need your approval in advance.

  5. AI use is disclosed. Your agreement names the AI tooling involved and explains how your data is handled.

Who does what

The agent

  • Maps the hosts, services and endpoints inside the signed scope
  • Checks them for known weaknesses and misconfigurations
  • Re-checks fixes after you have made them
  • Flags what it finds for the operator, with the evidence

The operator

  • Agrees the scope and the test window with you
  • Runs every exploit by hand; the agent does not exploit anything
  • Chains findings into the attacks that tools miss
  • Reproduces, rates and writes up every finding

Never without your sign-off

  • Any target outside the signed scope
  • Anything that could interrupt service or change data
  • Testing outside the agreed window

A harness we built ourselves

The testing agent runs inside a harness that Midnira wrote. Off-the-shelf autonomous testing tools let the model drive. For work on a client's live systems, we wanted the limits in code that we own and can show you. The model chooses what to look at next. Code decides whether it may.

Scope
Each target is checked against the signed authorization at the moment of contact. A name is looked up again every time, or tied to the server address written in the signed scope. A port scan is then given the approved addresses, not the name, and a web scan keeps the site's name but can only resolve it to the approved address. What cannot be verified is refused.
Options
Every tool has a short list of options it may use and speed caps the agent cannot lift. Anything else is refused.
Pace
One rate budget covers every worker, and only one scan runs against a host at a time, so agents running in parallel cannot crowd it.
Window
No scan starts outside the test window you signed, and one still running when the window closes is stopped.
Accounts
Scans run under a separate account, started only by the harness. The agent's own account has no route to your systems.
Record
Every decision goes into the log, the refusals too, with the exact command that ran.

No exploitation or denial-of-service tools are wired into it. Its tests run without touching a network, and each stage of the build gets a security review before the next begins. Our approval gate for AI operations was reviewed the same way: read what that review found.

scope.pyThe check every address goes through

# ---- direct IP target -------------------------------------------------
if kind == "ip":
    ip = _canon_ip(host)
    if ip is None:
        return ScopeDecision(DENY, target, kind, host, [],
                             "unparseable IP target")
    chost = str(ip)   # canonical form, used as the rate-limit key too
    for net in scope.exclude_cidrs:
        if ip in net:
            return ScopeDecision(DENY, target, kind, chost, [chost],
                                 f"ip in exclude_cidr {net}", str(net))
    # a special/non-public IP is in scope only if explicitly included
    if _is_special(ip) and not any(ip in net for net in scope.include_cidrs):
        return ScopeDecision(DENY, target, kind, chost, [chost],
                             "special/non-public IP not covered by an "
                             "explicit include_cidr")
    for net in scope.include_cidrs:
        if ip in net:
            return ScopeDecision(ALLOW, target, kind, chost, [chost],
                                 f"ip in include_cidr {net}", str(net),
                                 scan_ips=[chost])
    return ScopeDecision(DENY, target, kind, chost, [chost],
                         "ip not within any include_cidr")

The agent detects. It does not exploit.

The agent's vulnerability scanner can load the folders of checks listed here and no others. They are the ones that look for what a system exposes. The folders that confirm a weakness by exploiting it are not on the list.

Loaded
Thirteen folders, covering the technology in use, exposed files and admin panels, misconfigurations, takeover risks, network services, TLS and DNS.
Left out
Checks that confirm a weakness by exploiting it, default-password attempts and fuzzing. When a version number points to a known vulnerability, the agent flags it and the operator confirms it by hand.
Kept out
A folder added by a later update stays out until it has been reviewed. If the agent asks for an excluded category, the request is refused and logged.

A sample finding, as it appears in a report

Invoice API returns other customers' records

Severity
High
Where
GET /api/invoices/{id}

What happened

Changing the invoice number in a request returned an invoice that belongs to a different customer. The server checks that the caller is signed in. It does not check that the invoice is theirs.

Steps to reproduce

  1. Sign in as test customer A and open any invoice.
  2. Note the invoice number in the request, then request the next number up.
  3. The response contains customer B's name, address and line items.

Fix

Check ownership on the server for every invoice request, and add a test that fails if one customer can read another's invoice.

How to spot it

One signed-in account asks for invoice numbers in sequence, and most of them belong to other customers. Alert when a single session reads invoices from more than one customer account.

The questions buyers ask, answered.

Is it safe to run on production?
Yes, with limits. The agent maps and checks for known weaknesses at a controlled rate. Anything that could interrupt service or change data needs your approval in advance, and you choose the test window. We can also test a staging copy if you have one.
Who checks what the agent finds?
The operator. Every finding in your report has been reproduced by hand, so an agent's false alarm does not reach you.
What does the AI provider see?
The agents run on Claude, the AI model made by Anthropic. Test data that passes through the agents is not used for model training. Your agreement names the AI tooling and explains how your data is handled, including how long the provider keeps it.
Who sees our systems and data?
One person at Midnira: the founder, who runs your test. There are no subcontractors and no offshore staff, and Midnira is based in the United States. Anthropic processes the text the agents read, as the model provider.
How is the report delivered, and how long is the evidence kept?
The report and its evidence are sent to you encrypted. Your agreement sets how long the evidence is kept. It is then deleted, and the deletion is confirmed in writing.
Can we sign an NDA first?
Yes. We sign an NDA before the scoping call if you want one.
Can you test without AI?
Yes. A manual test uses no AI tooling, for environments where it is not permitted.
How is this different from a vulnerability scan?
A scan lists known weaknesses. A penetration test shows what an attacker can do with them: which can be exploited, how they chain together and what they expose. Each finding comes with the steps to reproduce it.
How long does it take?
Most tests run one to two weeks, and the report follows within five business days. The scoping call sets the dates.
Is a retest included?
Yes. One retest of the fixes is included in the price.
