Field note, November 22, 2026

We attacked our own approval gate before a client's documents went near it.

Midnira's approval gate decides whether a document an agent wants to file is actually filed. Before it carried any real work, we put it through a security review. The review found 14 things to fix. All 14 are fixed, and this note lists them.

Why review it

Everything the AI operations page says about approval rests on this one piece of code. An agent that has been misled by a cleverly worded document will try whatever it can reach, so the gate has to hold against the agent it serves. Code like that should be attacked early.

The gate's code and its real output are on the AI operations page.

How the review ran

Two AI reviewers worked separately, each on its own copy of the code. Neither saw the other's notes or the author's opinion of the code. One played an agent that had been turned against its operator and tried to get a document filed without approval. The other read every line and checked each sentence on our public page against what the code does. The author then made a third pass.

Every finding had to be reproduced before anything was changed. After the fixes, all three sets of proofs were run again on the fixed code.

What it found

  1. A filing could land with no record. If the record row could not be written, the document still moved. A row is now written and saved to disk before the document moves, and another after.
  2. A failed write could leave half a row. Record rows are now written whole or taken back out.
  3. An odd signature crashed the gate. A signature with unusual characters stopped it before anything was recorded.
  4. A blank fingerprint passed the record check. Checking the record against an empty fingerprint behaved as if none had been asked for.
  5. A weak signing key allowed forged approvals. A key of 32 zero bytes let anyone sign. Keys of that kind are now refused.
  6. The caller's settings could run code inside the gate. The tools now start without reading the caller's Python settings.
  7. A file could be swapped while it was being filed. A temporary file in the destination folder could be replaced, so the wrong document was filed under the approved name. A document now has no name until it is complete.
  8. Paths could be steered outside the store. Folders reached through symbolic links are no longer followed. Each path is walked one folder at a time.
  9. A deleted record quietly started again. The gate no longer creates the record. If the record is missing, or is not the gate's own, the gate stops.
  10. A giant path stalled everything. A proposal with a path half a million parts long held the record's lock for a minute. Named fields are now capped at 1,024 characters.
  11. Invisible characters disguised file names. A name could read as a PDF and be a program. Names that contain those characters are refused.
  12. The policy warning had blind spots. It missed two ways the calling account could still change the policy.
  13. The pointer to the gate's home could be redirected. It must now belong to the system administrator's account and be a full path. A bad one stops both tools.
  14. The help flag reported success. Asking for help exited with the same code as a completed filing.

What code alone does not settle

Some of what the review raised depends on how the gate is installed for a client. The gate has to run under its own account, which the agent's account cannot change. Run under the agent's own account it is a check and not a barrier, and it warns when the calling account could rewrite its policy. The folder that holds approvals belongs to the approval step alone, and each engagement gets its own signing keys. The record proves itself only against a fingerprint the client already holds, which is why one goes out with every report.

Two design questions are still open: whether an approval should expire, and whether the engagement should be written into each signature.

The numbers

The gate's tests went from 81 to 105. A mutation check, which breaks the code on purpose to see whether the tests notice, was caught 34 times out of 34. The gate has not yet run for a client. The review came first.

What we took from it

Most of the 14 were not in the approval logic. They were at the edges: files, paths, keys, settings and exit codes. A test of any system that puts an agent near something that matters should start there. That is how we approach penetration tests of AI applications and agents.
